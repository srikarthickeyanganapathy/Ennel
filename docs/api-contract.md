# ENNEL API Contract (draft)

Status: **Phase 1–4 endpoints implemented** (marked ✅, detailed in §2.1–2.3, §3.1 and §3.2). Conventions are fixed. The rest of the inventory is a plan, and each phase finalizes its endpoints here and in Swagger (`/api/docs`). Request/response schemas are the Zod schemas in `@ennel/shared/schemas`.

## 1. Conventions

| Topic       | Rule                                                                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Base paths  | Student `/api/v1`, staff `/api/v1/admin`                                                                                                       |
| Resources   | Plural kebab-case nouns (`/bookings`, `/no-show-appeals`); actions as sub-resources (`POST /bookings/{id}/cancel`)                             |
| JSON        | `camelCase`; dates `YYYY-MM-DD` (IST business date); instants ISO-8601 UTC (`2026-10-19T04:30:00.000Z`); clients format them in IST with AM/PM |
| Auth        | `Authorization: Bearer <access>`; refresh via `POST …/auth/refresh` with the refresh token in the body (mobile) or an httpOnly cookie (admin)  |
| Idempotency | `Idempotency-Key: <uuid>` **required** on booking create/change/cancel, leave create/extend/end, complaint create                              |
| Concurrency | Edited records carry `version`; send it back on PATCH; a stale version returns `409 VERSION_CONFLICT`                                          |
| Overrides   | Admin overrides require `reason` (non-empty, ≤500 chars), else `422 OVERRIDE_REASON_REQUIRED`                                                  |
| Request ID  | Responses carry `X-Request-Id`; also echoed in error bodies                                                                                    |

### 1.1 Lists

Query: `page` (≥1, default 1), `pageSize` (1–100, default 20), `sortBy`, `sortOrder` (`asc`|`desc`), `q`, plus resource filters.
Response: `{ "items": [...], "total": 123, "page": 1, "pageSize": 20 }`.

### 1.2 Errors

```json
{
  "code": "BOOKING_DEADLINE_PASSED",
  "message": "Cancellation closed at 10:00 AM.",
  "details": { "deadlineAt": "2026-10-19T04:30:00.000Z" },
  "requestId": "…"
}
```

| Code                       | HTTP | Meaning                                            |
| -------------------------- | ---- | -------------------------------------------------- |
| `VALIDATION_FAILED`        | 400  | Input failed schema validation (`details.issues`)  |
| `UNAUTHENTICATED`          | 401  | Missing/invalid/expired token or wrong audience    |
| `INVALID_CREDENTIALS`      | 401  | Login failed (no hint whether the account exists)  |
| `ACCOUNT_LOCKED`           | 423  | Lockout or staff-locked account                    |
| `PASSWORD_CHANGE_REQUIRED` | 403  | Staff must change password before other calls      |
| `PERMISSION_DENIED`        | 403  | Missing permission                                 |
| `NOT_FOUND`                | 404  | Resource missing or not visible to caller          |
| `VERSION_CONFLICT`         | 409  | Optimistic-lock mismatch                           |
| `IDEMPOTENCY_KEY_REUSED`   | 409  | Same key, different payload                        |
| `ROSTER_NOT_FOUND`         | 404  | Reference number not in the active roster          |
| `ALREADY_REGISTERED`       | 409  | Reference number already has an account            |
| `BOOKING_DEADLINE_PASSED`  | 422  | Cancel/change/diet deadline passed                 |
| `SLOT_UNAVAILABLE`         | 422  | Slot full (no over-capacity), disabled, or closed  |
| `BOOKING_NOT_ALLOWED`      | 422  | Date outside horizon, on leave, or mess closed     |
| `LEAVE_RANGE_INVALID`      | 422  | End before start, overlap, or invalid resume point |
| `OVERRIDE_REASON_REQUIRED` | 422  | Missing reason on an override                      |
| `ROSTER_IMPORT_INVALID`    | 422  | Import confirm attempted with blocking errors      |
| `FILE_INVALID`             | 422  | Upload type/size invalid                           |
| `RATE_LIMITED`             | 429  | Too many requests                                  |
| `INTERNAL_ERROR`           | 500  | Unexpected failure (no internals leaked)           |

### 2.1 Phase 1 endpoints

Bodies are validated with the named `@ennel/shared` schema; errors use §1.2. `AuthSession` = `{ accessToken, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt, isOnboardingComplete }`.

| Endpoint                  | Body → response                                                   | Errors                                                                                                                                        | Notes                                                                                                                                                                                  |
| ------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /auth/roster-check` | `rosterCheckRequestSchema` → `{ status: NEW \| REGISTERED }`      | `ROSTER_NOT_FOUND` (unknown or inactive)                                                                                                      | Reference number normalized to digits. 20/min per IP                                                                                                                                   |
| `POST /auth/register`     | `registerRequestSchema` → `AuthSession` (201)                     | `VALIDATION_FAILED` (incl. "Passwords do not match."), `ROSTER_NOT_FOUND`, `ALREADY_REGISTERED`                                               | Copies college data from the roster. 10/min per IP                                                                                                                                     |
| `POST /auth/login`        | `loginRequestSchema` → `AuthSession`                              | `INVALID_CREDENTIALS` (same for unknown accounts), `ACCOUNT_LOCKED` (`details.lockedUntil`; also locked/deactivated accounts), `RATE_LIMITED` | 5 failures → 15-minute lock. 10/min per IP                                                                                                                                             |
| `POST /auth/refresh`      | `{ refreshToken }` → `AuthSession`                                | `UNAUTHENTICATED`, `ACCOUNT_LOCKED`                                                                                                           | Rotates the token. Reusing an old token revokes the whole session family, so clients refresh one at a time                                                                             |
| `POST /auth/logout`       | `{ refreshToken }` → 204                                          | none                                                                                                                                          | Revokes the session family; unknown tokens are ignored                                                                                                                                 |
| `GET /me`                 | → `StudentProfile`                                                | `UNAUTHENTICATED`                                                                                                                             | Includes `editableFields` and a signed `photoUrl` (15 minutes)                                                                                                                         |
| `PATCH /me/profile`       | `updateProfileRequestSchema` (incl. `version`) → `StudentProfile` | `VALIDATION_FAILED` (college-controlled field, unknown block), `VERSION_CONFLICT`                                                             | Unknown fields are rejected                                                                                                                                                            |
| `PUT /me/photo`           | multipart field `photo` → `StudentProfile`                        | `FILE_INVALID`                                                                                                                                | JPEG/PNG/WebP/HEIC detected from content, ≤5 MB; replaces the previous photo                                                                                                           |
| `PUT /me/onboarding`      | `completeOnboardingRequestSchema` → `StudentProfile`              | `VALIDATION_FAILED` (paths `mealPreferences.<MEAL>`)                                                                                          | One transaction: profile, 3 meal preferences, `onboardingCompletedAt`. College-controlled values are ignored. Upcoming Default Bookings are created in the same transaction (BR-DEF-4) |
| `GET /hostels`            | → `{ items: HostelOption[] }`                                     | `UNAUTHENTICATED`                                                                                                                             | Active hostels and blocks                                                                                                                                                              |
| `GET /meals`              | → `{ items: MealConfig[] }`                                       | `UNAUTHENTICATED`                                                                                                                             | Active meals in serving order with active slots                                                                                                                                        |

### 2.3 Phase 4 endpoints (booking engine)

Writes need an `Idempotency-Key` header (a UUID, ADR-0016): a retry with the same key and request replays the first response; the same key with a different request returns `409 IDEMPOTENCY_KEY_REUSED`; a missing key returns `400 VALIDATION_FAILED`. Each write returns the updated meal card (`mealCardSchema`), so the app can redraw that one card.

| Endpoint                            | Body → response                                                             | Errors                                                                                                                                                                                | Notes                                                                                                                                                                                                                                                          |
| ----------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /days/{date}`                  | → `DayResponse` (3 meal cards)                                              | `BOOKING_NOT_ALLOWED` outside today … today + horizon                                                                                                                                 | Each card has `label` (BR-BOOK-3), `appliedRule` (ADR-0014), the booking (slot, meal type, status, source, `isUpdatedByStaff`, `version`) and `actions.book / changeSlot / changeDiet / cancel`, each with `allowed`, `reason` and `deadlineAt` for countdowns |
| `POST /bookings`                    | `bookMealRequestSchema` → card (201)                                        | `SLOT_UNAVAILABLE` (full, disabled, started, wrong meal), `BOOKING_NOT_ALLOWED` (closed, on leave, already booked, outside the period)                                                | Writes a one-day BOOK date exception and the booking (source `MANUAL`) in one transaction; the seat is checked under the slot/date lock (ADR-0004). A cancelled meal can be booked again                                                                       |
| `PATCH /bookings/{id}`              | `changeBookingRequestSchema` (`slotId` and/or `dietType`, `version`) → card | `BOOKING_DEADLINE_PASSED` (slot change closes at slot start, meal type `dietTypeChangeCutoffMinutes` before), `SLOT_UNAVAILABLE`, `VERSION_CONFLICT`, `NOT_FOUND` (not the student's) | This date only; recurring preferences are untouched (Rule 5)                                                                                                                                                                                                   |
| `POST /bookings/{id}/cancel`        | → card                                                                      | `BOOKING_DEADLINE_PASSED` (`cancellationCutoffMinutes` before slot start), `NOT_FOUND`                                                                                                | Writes a SKIP date exception, so the nightly job never re-creates it                                                                                                                                                                                           |
| `POST /days/{date}/cancel-eligible` | → `{ cancelled, notEligible[{ mealType, reason }], day }`                   | `BOOKING_NOT_ALLOWED`                                                                                                                                                                 | Spec §4.4, BR-DEAD-6                                                                                                                                                                                                                                           |

### 2.5 Phase 6 endpoints (Plan Ahead weekday rules)

Student session required. A one-date change from Plan Ahead uses the Phase 4 booking endpoints, exactly as Home does (BR-PLAN-1). Every rule write re-syncs upcoming bookings in the same transaction and returns the fresh list (BR-PLAN-3, ADR-0024).

| Endpoint                               | Request → response                                                                                               | Errors                                                                                                                                  | Notes                                                                                                                                                                                           |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /weekday-rules`                   | → `{ items: WeekdayRule[] }`                                                                                     | `UNAUTHENTICATED`                                                                                                                       | Active rules in meal order: `mealType`, `mealName`, `weekdays` (0 = Sunday, IST), `slotId`, `slotLabel`, `dietType`, `version`, `pausedReason` (`DEFAULT_BOOKING_OFF`, `AUTO_DISABLED` or null) |
| `POST /weekday-rules`                  | `createWeekdayRulesRequestSchema` (`weekdays`, `meals: [{ mealType, slotId, dietType }]`) → `WeekdayRuleResult`  | `VALIDATION_FAILED` (no days, duplicate meals, slot not of that meal, overlapping days for a meal; paths `weekdays`, `slotId`, `meals`) | One rule per meal, created together. 201                                                                                                                                                        |
| `PATCH /weekday-rules/{id}`            | `updateWeekdayRuleRequestSchema` (any of `weekdays`, `slotId`, `dietType`, plus `version`) → `WeekdayRuleResult` | `VALIDATION_FAILED`, `NOT_FOUND` (not this student's active rule), `VERSION_CONFLICT`                                                   |                                                                                                                                                                                                 |
| `DELETE /weekday-rules/{id}?version=n` | → `WeekdayRuleResult`                                                                                            | `NOT_FOUND`, `VERSION_CONFLICT`, `VALIDATION_FAILED` (missing version)                                                                  | The row is kept inactive; those days return to Default Booking                                                                                                                                  |

`WeekdayRuleResult` is `{ items: WeekdayRule[], bookingsUpdated }`.

### 2.7 Phase 8 endpoints (Leave, Spec §11, ADR-0026)

Student session required. Leave errors on the range use `LEAVE_RANGE_INVALID` (422): end before start, start before the earliest allowed meal, overlap with another pending or approved leave, more than 366 days, a resume point outside the leave, or an extension that does not move the end later.

| Endpoint                   | Request → response                                                    | Notes                                                                                                                                                                                             |
| -------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /leaves`              | → `LeavesResponse`                                                    | `current` (`NOT_ON_LEAVE`, `UPCOMING`, `ON_LEAVE`, `PENDING` and the leave), `items` (newest first, each with derived `state`, `days`, `meals`, `canChange`), `earliestStart`, `requiresApproval` |
| `POST /leaves/preview`     | `applyLeaveRequestSchema` → `LeavePreview`                            | `days`, `meals`, `status` it would get, `bookingsToPause`, `earliestStart`, `problem` (text or null). Never fails on a bad range; it explains it                                                  |
| `POST /leaves`             | `applyLeaveRequestSchema` (range + optional `reason`) → `LeaveResult` | Needs `Idempotency-Key`. `APPROVED` at once unless `leaveRequiresApproval`, then `PENDING`. 201                                                                                                   |
| `GET /leaves/{id}`         | → `Leave`                                                             | `NOT_FOUND` for another student's leave                                                                                                                                                           |
| `POST /leaves/{id}/extend` | `{ endDate, endMealType, version }` → `LeaveResult`                   | With approval on, an approved leave gets `extensionRequest` (a new pending leave) instead. `VERSION_CONFLICT` on a stale version                                                                  |
| `POST /leaves/{id}/end`    | `{ resumeDate, resumeMealType, version }` → `LeaveResult`             | The first meal to book again; at or before the start, the leave is `CANCELLED`                                                                                                                    |

`LeaveResult` is `{ leave, extensionRequest, bookingsPaused, bookingsResumed }`.

### 2.9 Phase 10 endpoints (Complaints and notifications, Spec §12–13, ADR-0008, ADR-0028)

Student session required.
